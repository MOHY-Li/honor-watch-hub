# SPEC：WatchHub 2.2.0 — 后台耗电优化 + 信息架构收口

- 日期：2026-10-23
- 状态：已实现（2026-10-23）
- 关联版本：versionCode 20200 / versionName 2.2.0
- 作者：lead

## 1. 问题

**耗电**（代码位置 `service/HubService.kt`）：前台服务每 20 秒无条件跑一整套动作：

- `engine.materialize()` 每 20 秒把未来 7 天的任务重算一遍（实际每小时一次就够）；
- `scheduler.armAt(next)` 每 20 秒重设一次精确闹钟（只有目标时间变化时才需要）；
- `update(summary())` 每 20 秒重算两次 DB 统计并刷新常驻通知（文案不变时没必要）；
- 持有 PARTIAL_WAKE_LOCK 并每轮续期，等于常驻持锁。

**信息架构**：

- 任务页用 `ConcatAdapter(taskAdapter, reminderAdapter)` 把「任务」和「提醒规则管理」拼在同一滚动区，管理提醒要滑到底，且完成/删除操作相邻易误触；
- 「源」和「订阅」都能添加 RSS 源：源页走 JSON 模板、订阅页走自动发现，配置和阅读分居两页，用户不知道去哪加；
- 首页 6 个区块，「最近推送」与订阅页文章/通知历史重复；
- 设置页把配置（自启/日历/镜像）、诊断（体检/日志/测试）、更新混在一起。

## 2. 用户场景

1. 用户息屏放着手机一整天，希望提醒照常触发，但不愿中枢持续吃电。
2. 用户想快速处理今天的任务，不想在一屏里同时面对「任务」和「规则开关」。
3. 用户想加一个 RSS，应该只有一个自然入口；加完在订阅页读，规则调整在源页。
4. 用户排障时能一次找到体检/日志/测试通知，而不是在设置页翻。

## 7. 边界与失败情况

| 场景 | 期望 |
|---|---|
| `nextDueAt == null`（没有待办） | 60s 间隔；闹钟取消（沿用现有 cancel 逻辑） |
| 任务刚过期未处理（nextDue <= now） | 20s 间隔，让服务 tick 尽快补处理 |
| 服务刚启动，`lastMaterializeAt = 0` | 立即 materialize |
| 系统时间被回拨 | 缓存 TTL 判定不能返回负数；策略函数对 now < last 视为过期重算 |
| 闹钟目标为 null → null | 不重复 cancel，不重复 set |
| 通知文案相同但推送条数变化 | 文案里含条数，条数变化即文案变化，需要刷新；相等才跳过 |
| 首页不可见 | 停止 ticker（已有逻辑，保持） |
| 新页面在提醒被删除后返回 | 任务页/新页面 onResume 刷新，不崩溃 |
| 订阅源被删除后从卡片点编辑 | 编辑页提示「数据源不存在」并 finish（已有行为） |

## 11. 决策记录

grilling 第 1 轮（范围与精度）：

- 2.2.0 范围 = 耗电优化 + 信息架构收口（不做 RSS 过滤/OPML，留 2.3.0）。
- 后台轮询采用自适应 tick：有 2 分钟内到期任务 20s，否则 60s；提醒准点性由精确闹钟保证。

grilling 第 2 轮（IA 细节）：

- 提醒管理放独立二级页（`ReminderListActivity`），任务页只留任务与入口。
- 订阅卡片增加「编辑」，跳转到同一个源编辑页；订阅页不再重复实现编辑。
- 首页「最近推送」区块直接删除，历史统一在订阅页/通知详情查看。
- 设置页内分四组：通知与手表 / 自动化 / 诊断 / 关于；诊断不做独立一级入口。
