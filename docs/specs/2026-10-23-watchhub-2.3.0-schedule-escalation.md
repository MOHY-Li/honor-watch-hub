# SPEC：WatchHub 2.3.0 — cron/间隔调度 + 确认升级链 + 首页数据源状态

- 日期：2026-10-23
- 状态：实现中（纯逻辑已完成，接线/UI 待做）
- 关联版本：versionCode 20300 / versionName 2.3.0
- 作者：lead

## 1. 问题

1. 现有提醒只支持「星期 + 固定时间点」，无法表达「每 25 分钟一次」或 cron 表达式。
2. 提醒发出后如果用户没处理，就只响一次；用户希望「没得到确认就越来越频繁地提醒」。
3. 手表端无法回传已读/操作（平台事实），需要把确认动作放到手机上，并且明确告知用户。
4. 首页只显示「N/M 个源正常」，看不到每个数据源（RSS/JSON/正则/指纹）的具体状态。

## 2. 用户场景

1. 用户设置「每 25 分钟提醒喝水」；25 分钟后没在手机上确认，20 分钟后再次提醒，仍未确认 15 分钟后……一直到 1 分钟一次，直到确认。
2. 用户设置 cron 表达式（如工作日 9 点的日报提醒）；未确认时同样进入升级链；下一次 cron 到点重置阶梯。
3. 提醒触发时手机弹出确认窗口，用户可以点「完成 / 稍后 / 跳过」；通知上的按钮同样有效。
4. 用户打开首页能看到所有数据源的状态（包括番剧 JSON 源、RSS、正则、指纹），异常源排在最前面。

## 5. 非目标

- 手表端按钮/回执（平台不开放，明确告知用户）。
- cron 的秒字段、`@daily` 别名、月份/星期英文名（可留后续）。
- 自定义升级阶梯（先用固定 25/20/15/10/5/1）。
- 多设备同步。

## 6. 影响面

- **模型**：`Reminder` 增加 `mode`（times/interval/cron）、`intervalMin`、`cronExpr`、`escalationLadder`；`Task` 增加 `escalationLevel`、`lastNudgedAt`、`chainStartedAt`。
- **DB v4**：`reminders` 补 4 列、`tasks` 补 3 列；迁移默认值保证旧数据可用。
- **引擎**：`ReminderEngine` 负责按 mode 计算下一次触发、升级链推进/重置、确认动作；`Scheduler` 仍只负责精确闹钟。
- **服务**：升级链激活时进入 fast tick + 短唤醒锁（复用 ServicePolicy，增加 `hasActiveEscalation()`）。
- **送法**：`Notifier` 增加 actions（完成/稍后）、可选 full-screen intent；新增 `ReminderNudgeActivity`。
- **UI**：任务编辑页增加模式切换（固定时间 / 固定间隔 / cron）+ 对应字段；首页增加数据源状态列表。
- **首页数据**：`HubUi.Home` 增加 `sourceStates`，移除 `sourcesOk/sourcesTotal`（或保留计数同时给列表）。
- **文档**：README（调度/升级/确认/首页）、ARCHITECTURE（升级链状态机）、AGENTS（升级链规则）。

## 7. 边界与失败情况

| 场景 | 期望 |
|---|---|
| cron 表达式非法（字段越界、字段数不对） | 保存时拒绝并提示；不写入 DB |
| cron 一年内无解（如 2 月 30 日） | `nextAfter` 返回 null，提醒不排期，日志提示 |
| 间隔模式跨天 | 本地日期变化时阶梯重置为 0 |
| 确认窗口被划掉未选择 | 视为未确认，升级链继续 |
| 全屏意图权限被拒（Android 14+） | 退化为高优先级通知 + 操作按钮 |
| 用户手动「稍后 10 分钟」 | 链暂停到 10 分钟后，之后回到基础 25 分钟 |
| 设备处于 Doze | 升级期间保活策略缓解；仍可能受系统限制，日志记录实际触发偏差 |
| 旧版本任务（escalation_level 默认 0） | 按未升级状态正常处理 |

## 11. 决策记录

grilling 第 1 轮：

- 调度：固定间隔 + 标准 cron 两种都要。
- 确认来源：手表无法回传，改为手机端弹出确认窗口（用户选择）；通知按钮同效。

grilling 第 2 轮：

- 升级阶梯：25 → 20 → 15 → 10 → 5 → 1，之后每 1 分钟直到确认；跨天重置。
- cron 模式也升级，下一次 cron 触发重置阶梯。
- 升级期间保活（20s tick + 短唤醒锁），接受更高耗电。
- 首页：列出全部数据源状态，异常置顶。
