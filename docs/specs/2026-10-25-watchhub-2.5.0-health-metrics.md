# SPEC：WatchHub 2.5.0 — 健康指标域（展示 + 阈值告警 + AI 分析）

- 日期：2026-10-25
- 状态：已实现（架构与规则引擎落地；Health Kit 真实读取层待开发者资格过审后接入）
- 关联版本：versionCode 20500 / versionName 2.5.0
- 作者：lead
- 增补：2026-10-25 用户追加需求「接入 DeepSeek API 对指标做模型分析，记录整体情况与建议报告」，
  并入本版（见 §12）

## 1. 问题

手表 5 Pro 测得的心率/血压（趋势）/血氧/压力等指标全部留在「荣耀运动健康」App 里，
WatchHub 作为提醒中枢看不到身体状态，无法基于指标触发提醒；用户也希望在 App 内直接看到最新值。

通路调研结论（2026-10-25，来源见 README 参考链接）：

- **荣耀 Health Kit**（developer.honor.com，doc 11005）是唯一正道：官方数据类型含
  心率/血压/血氧/睡眠等，端侧读取无需服务器。前提：开发者账号 + 应用注册（绑证书指纹）
  + 逐项申请 scope 过审 + 用户在运动健康内授权；**主要绑定荣耀手机（MagicOS）**。
  用户已确认手机是荣耀、愿意申请。
- Health Connect + Health Sync 桥：免审核但依赖第三方付费 App 做桥，链路脆弱，不采用。
- 直连手表蓝牙 / 读运动健康私有存储：不可行。

**本版交付策略**：凭据无关的部分全部落地并测试（模型/规则引擎/采样管道/存储/UI/体检项），
读取层留 `HealthMetricsReader` 接口 + 默认「未接入」实现；资格过审后只需补一个
`HonorHealthKitReader` 适配器，其余零改动。

## 2. 用户场景

1. 首页看一眼：心率 68（5 分钟前）、血氧 98%、血压 122/81——不用打开运动健康。
2. 规则：「心率 > 100 持续 30 分钟 → 高优先级提醒」。命中后手表震动，通知写明
   「心率偏高 112 · 最近 30 分钟均高于 100」。
3. 规则带冷却（默认 60 分钟）：持续异常期间不刷屏，恢复后再次异常会再报。
4. 手表摘掉/数据停更：最新样本超过 15 分钟视为过期，不评估规则（防止旧样本误报，
   特别是「低于阈值」类规则），卡片显示「X 小时前」。
5. Health Kit 还没接入时：首页与体检页明确显示「未接入」，规则照常可建，不误报。

## 3. 验收标准（可执行）

| # | 验收标准 | 验证方式 |
|---|---|---|
| A1 | `HealthRuleEngine.evaluate`：窗口内（最近 sustainedMin 分钟）≥2 个样本且全部满足阈值 → HIT | `HealthRuleEngineTest.sustainedAboveHits`（先红后绿） |
| A2 | 窗口内有任一样本不满足、或样本不足 2 个 → NOT_HIT（单尖峰不告警） | `...spikeDoesNotHit` / `...singleSampleNotEnough` |
| A3 | BELOW 方向判定与 ABOVE 对称 | `...sustainedBelowHits` |
| A4 | 最新样本距今 > 15 分钟 → STALE，不产生告警 | `...staleDataNotEvaluated` |
| A5 | 命中后 cooldownMin 内 → COOLDOWN；超过后可再次 HIT | `...cooldownBlocks` / `...cooldownExpires` |
| A6 | 告警文案包含规则名、最新值、阈值语义 | `...alertTextContainsValues` |
| A7 | `MetricType.isValid` 按医学常识范围校验（心率 30–220、血氧 70–100、收缩压 80–200、舒张压 50–130、压力 0–100） | `MetricTypeTest` |
| A8 | DB v5：新增 `metrics` / `health_rules` 表，旧版本升级不丢数据 | 代码审读（onUpgrade 路径）+ 覆盖安装人工验证 |
| A9 | HealthEngine：采样节流 5 分钟；告警 key=`health:{ruleId}:{最新样本时间}` 保证同一批样本只落一条；命中后写 last_alert_at | 代码审读（引擎依赖 Android SQLite，seam 在纯函数） |
| A10 | 首页显示指标卡（最新值+时间，未接入时显示提示）；任务页新增「健康规则」区块（表单增删改/启停）；体检页新增「健康数据」项 | 人工 |
| A11 | 既有单测全绿（`TZ=UTC` 复跑）；assembleDebug、lintDebug 0 error | gradle |

## 4. 测试 seam（观察点）

- seam 1：`core/HealthRuleEngine.evaluate(rule, samples, now, lastAlertAt)` —— 规则判定全部语义
  （HIT/NOT_HIT/COOLDOWN/STALE）与告警文案构造，纯函数全覆盖。
- seam 2：`core/model/Health.MetricType.isValid(value)` —— 表单校验范围。
- seam 3：`HubUi.home()/healthRuleRows()/saveHealthRule()` —— 展示与 CRUD 门面，人工清单。
- 不测：MetricStore/HealthRuleStore 的 SQL（与既有 store 层一致，无 JVM SQLite）；
  HealthEngine 的编排（依赖 store）；UI 渲染。

## 5. 非目标

- **不做 Health Kit SDK 接入**（资格未批）：不做假数据、不做「模拟指标」开关。
- **不做历史趋势图**：荣耀运动健康自己的趋势图更好，抄一遍就是刚删掉的那种冗余；
  本域只显示最新值。
- 不做指标写入运动健康、不做云同步、不做医疗建议（告警只是用户自定义阈值的提示）。
- 不做 ECG/HRV/睡眠结构等复杂类型（MVP 五项：心率/血氧/收缩压/舒张压/压力）。

## 7. 边界与失败情况

| 场景 | 期望 |
|---|---|
| Health Kit 未接入 | 首页/体检显示「未接入」；规则可建可存，不评估（无样本自然 STALE） |
| 采样抛异常（未授权/服务不在） | 记日志，本轮跳过，样本照旧，STALE 保护兜底 |
| 手表摘掉、数据停更 >15min | 规则不评估；首页显示最后时间 |
| 同一批样本重复评估 | key 幂等（`health:{ruleId}:{样本时间}`），AlertStore 唯一索引拒绝 |
| 持续异常 | cooldown（默认 60min）内只报一次；last_alert_at 落库，重启后仍生效 |
| 进程被杀 | 样本/规则/last_alert_at 全在 SQLite，重启恢复；未送达 Alert 走既有 PENDING 补发 |
| 旧版本覆盖升级 | onUpgrade 建 v5 表，既有数据不动 |
| 采样间隔（5min）内多次 tick | 只评估不采样（节流），评估是纯内存+本地读，代价可忽略 |
| 指标值明显异常（如心率 0） | reader 侧丢弃 `!MetricType.isValid` 的样本 |

## 11. 决策记录（人工 grilling）

Q1 只做展示还是做告警？——只展示 = 复刻运动健康仪表盘（冗余）；只告警不展示 = 用户看不到
当前值无法理解告警。取两者：展示最新值（一行一指标，不做图表）+ 阈值告警（复用 Alert 管道，
这是 WatchHub 的差异化）。用户确认「两者都要」。

Q2 持续语义怎么定？——「窗口内全部样本满足且 ≥2 个」而不是「滑动平均」或「连续 N 个」：
平均会掩盖低值尖峰，「全部满足」最直观可解释（「最近 30 分钟每次测都超」）。单样本不告警。

Q3 为什么 15 分钟新鲜度门槛？——采样间隔 5 分钟，容忍一次采样失败；超过则大概率手表
摘掉/蓝牙断开，此时 BELOW 类规则用旧值判断会误报。宁可漏报不可误报（告警疲劳比漏报更毁产品）。

Q4 为什么规则放任务页？——任务页已是「规则的家」（提醒规则在此）；健康规则与提醒规则同构
（都是「条件 → 提醒」），放一页符合信息架构；设置页是配置不是规则。

Q5 为什么 MVP 不接 SDK？——SDK 需要过审的 AppID 才能初始化，未过审时写出来无法运行
也无法测试（违反 TDD 原则）；接口已按官方 demo 的数据形态（`com.hihonor.mcs.fitness.health`）
预留，适配层是纯增量。

Q6 为什么不做趋势图？——见非目标。运动健康的趋势分析更强；本域的值在「触发规则」，
不在「回顾数据」。

## 12. 增补：AI 分析（DeepSeek）

### 问题与方案

用户要求在指标展示之上接 DeepSeek API：对近期指标做模型分析，**记录**整体情况报告与建议报告。

- **数据流**：`MetricStore(7 天样本聚合统计) + 规则命中数 → engine/HealthAnalyst（编排）
  → source/DeepSeekClient（HTTP，OpenAI 兼容协议）→ 报告落库（health_reports 表）
  → 首页查看 + 自动分析完成时发一条 NORMAL 通知`。
- **触发**：手动（首页「AI 分析」按钮）+ 每周自动（设置开关，默认关；服务维护周期检查，
  分析在线程池跑，不阻塞心跳线程）。
- **配置**：设置页「AI 分析」组：API Key（密码框，存 settings 表，绝不写日志）、每周自动开关。
- **架构合法性**：AGENTS §8「不引入服务器或公网依赖；中枢离线可用（数据源自身的网络访问除外）」
  ——DeepSeek 调用与 RSS 抓取同类（外部数据源的网络访问），失败只影响分析本身，
  提醒/告警等核心能力不受影响。依赖方向：`engine → source(DeepSeekClient) → net`，合法。
- **隐私**：只上传**聚合统计**（每指标的样本数/最新/最小/最大/均值 + 时间窗），
  不上传原始逐条样本；报告只存本地。

### 验收标准（增补）

| # | 验收标准 | 验证方式 |
|---|---|---|
| A12 | `HealthAnalyst.summarize` 聚合统计（count/min/max/avg/latest）来自手工算例 | `HealthAnalystTest.summarizeStats`（先红后绿） |
| A13 | `HealthAnalyst.buildPrompt` 包含各指标统计值与数据不足提示 | `HealthAnalystTest.promptContainsStats` |
| A14 | `DeepSeekClient.parseContent` 解析 OpenAI 兼容响应取 `choices[0].message.content`；错误响应返回 null | `DeepSeekClientTest` |
| A15 | 设置页可保存 API Key 与每周自动开关；Key 不出现在日志 | 人工 |
| A16 | 手动分析：无 Key 提示先去设置；成功后报告入库存档、弹窗展示；失败弹原因 | 人工（需真实 Key） |
| A17 | 每周自动：开关开启且距上次 >7 天时在服务维护期触发，完成发一条通知 | 人工（需真实 Key） |
| A18 | 报告历史保留最近 20 份，旧报告自动清理 | 代码审读 |

### 边界（增补）

| 场景 | 期望 |
|---|---|
| 无 API Key | 手动分析直接提示「先在设置里填 API Key」，不发起请求 |
| Key 无效 / 余额不足 / 限流 | 分别映射为明确错误文案；报告不入库 |
| 网络超时（默认 120s 上限） | 报错，不影响中枢其他功能 |
| 样本不足（任一指标样本 <5 条） | 仍可分析，prompt 注明「数据不足」让模型直说 |
| 分析线程与心跳线程隔离 | 分析在新线程，绝不阻塞服务循环/看门狗 |
| API 协议与官方文档不一致 | DeepSeekClient.parseContent/buildRequest 为纯函数，修协议不改编排 |

### 决策（增补）

- 模型固定 `deepseek-chat`（协议 OpenAI 兼容；不做模型选择 UI，YAGNI）。
- 报告不进手表正文（>120 字会被镜像截断），只发「已生成」提示；全文在手机看。
- 未拿到用户 API Key 前无法真机联调：协议实现按 DeepSeek 官方文档写，
  `parseContent/buildRequest` 纯函数有单测，真实调用列入人工验证清单。
